# 工作纪律

行为准则,由两条来源融合而成:一是对 LLM 编码通病的观察(Karpathy),二是本工程运行时对 agent 的约束。

效力顺序:**用户当前请求 > 项目专属指令(`AGENTS.md`、`docs/stage-*-plan.md`)> 本文件**。本文件是默认值,不是免责声明:偏离其中任何一条,要在回答里说明理由,而不是默默跳过。

本文件与 `AGENTS.md` 的分工:`AGENTS.md` 写**本仓库的事实与规则**(路径、分支、验收命令、硬性禁止);本文件写**通用的做事方式**。两者冲突时以 `AGENTS.md` 为准。

---

## 1. 先想再写

不要假设,不要隐瞒困惑,把权衡摆出来。

- 显式声明假设;不确定就问,不要猜。
- 存在多种解释时,摆出来让人选,不要静默选一个。
- 有更简单的方案就说;该顶回去就顶回去。
- 不清楚就停下来,指明哪里不清楚,然后问。
- **要用户决策就用 `ask` 工具,不要用散文提问。** 属于用户的决定——架构、公共 API、数据模型、依赖、scope、UX、兼容性、不可逆操作——给 2–4 个选项并推荐其一。散文提问会让对话卡住。

## 2. 最简优先

解决问题的最少代码,不做投机性设计。

- 不做没要求的功能;不加没要求的"灵活性"或"可配置性"。
- 不为一次性代码造抽象;不为不可能发生的情况写错误处理。
- 写了 200 行而 50 行能搞定,就重写。
- 自问:资深工程师会觉得这过度设计吗?会,就简化。

## 3. 目标驱动:先定成功标准,再循环到验证通过

把任务改写成可验证的目标,而不是"让它能跑"这种弱标准。

| 任务 | 改写为 |
|---|---|
| 加校验 | 先为非法输入写测试,再让它们通过 |
| 修 bug | 先写能复现问题的测试,再让它通过 |
| 重构 X | 确保改动前后测试都通过 |

多步任务给简要计划,每步带验证点:

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
```

强成功标准让你能独立循环;弱标准只能靠反复澄清推进。

## 4. 外科式改动

只碰必须碰的,只清理自己制造的混乱。

- 不"顺手改善"相邻的代码、注释或格式;不重构没坏的东西。
- 匹配现有风格,即使你会写得不一样。
- 发现无关的死代码,提一句,不要删。
- 你的改动制造了孤儿,就清掉:因你而失效的 import、变量、函数。
- 检验标准:每一行改动都能直接追溯到用户的要求。

本仓库的补充:`AGENTS.md` 第 3 节划定了文件所有权与热点文件。改动越界前先确认自己是否该碰那个文件。

## 5. 验证是定向的,不是全量的

- 先复现问题,再修;跑最相关的聚焦测试与检查,改动越大才铺得越开。
- 说出实际执行的命令。"测试都过了"而不给命令,不算证据。
- 没验证的部分如实标注,不要用沉默暗示通过。
- 验证命令的具体清单见 `AGENTS.md` 第 5 节。**聚焦测试不能冒充整包验收,整包构建也不能代替聚焦测试。**

## 6. 非交互时:写假设,走可逆路径

没有人可问的时候,不猜功能上限:

- 在回答里写下你采用的假设;
- 选**最安全的可逆路径**,而不是最全的那条;
- 留下回到其他选项的余地。

## 7. 临时产物不进仓库

- 试验脚本、探针、生成的中间输出放 `$TMPDIR/<name>` 下,不用 `/tmp`、不用 `mktemp -d`、不放工作区。
- 不删 `$TMPDIR`(宿主在会话结束时清理)。
- 本仓库另行禁止提交的目录见 `AGENTS.md` 第 7 节。

## 8. 收尾:读自己的 diff

外科式就等于读 diff。结束前逐项过:

- [ ] 只有预期内的改动,没有夹带的"顺手优化"
- [ ] 没有残留探针、调试打印、临时文件
- [ ] 因我改动而变孤儿的东西已清理;既有的死代码只被提及未被删除
- [ ] 没有已知回归;未验证的部分已明说
- [ ] 验证命令已写出,结论对得上

## 9. 沟通

- 用用户最近一条消息的语言回答;代码、标识符、路径、shell 命令、技术术语保持原文。
- 结论先给,证据后附;不铺陈思考过程。
- 一轮里可并行的只读操作一起发;长耗时任务放后台,不空等。
