## 一、目标、范围与总体方案

制作一个可独立启动的 Windows 桌宠：角色使用真实 3D 模型与骨骼动画，在屏幕工作区底边走动，可拖拽、基础抛落、聊天、记住偏好、朗读回复并同步口型。

截至 2026 年 11 月 1 日，已经完成参考源码阅读和 4 项纯算法检查；Godot 窗口穿透、VRM 动画、原生扩展及最终打包效果仍属于待验证项目。

### 1.1 已确认的产品选择

| 项目 | 首版决定 |
|---|---|
| 平台 | Windows 11 x64，优先验收当前电脑 |
| 运行方式 | 独立程序，不要求启动旧桌宠或 LFTTDO |
| 技术组织 | Godot + 精简 Python 服务 |
| 角色 | 同时显示一只；支持由 VRM / GLB / glTF 制作的预制人形角色包，切换时复用同一套标准动作 |
| 动作复用 | 一套人形动作源库；新模型首次完成骨骼和表现适配，之后切换无需修改聊天和行为代码 |
| 活动范围 | 工作区底边走动，拖起后可自然落下 |
| AI | 用户选择云端或本地兼容接口 |
| 语音 | 朗读回复、口型、停止播放；输入以文字为主 |
| 点击判断 | 随骨骼移动的身体交互区，明显空白穿透 |
| 首版暂缓 | 多宠、窗口边缘攀爬、持续语音、主动识屏、音乐联动、灵动岛、通用工具执行 |

“独立”指桌宠自身完成界面、会话、记忆和服务管理。本地大模型由用户配置的模型服务提供，首版安装包不附带大模型权重。

### 1.2 总体结构

```text
Pet3D.exe：Godot 主程序
├─ 透明角色窗口、聊天窗口、设置、托盘
├─ VRM / GLB / glTF 角色适配、共享动作库、表情、口型
├─ 本地行为、拖拽、屏幕边界
├─ Windows 原生适配模块
└─ 自动启动和管理 pet-service.exe
   ├─ 模型接口与流式回复
   ├─ 会话与长期记忆
   ├─ 语音合成
   └─ 配置、凭据、持久化
```

采用一个角色小窗口，聊天和设置使用可正常获得焦点的独立窗口。首版不沿用旧项目覆盖整个虚拟桌面的合成窗口。

用户只需要启动桌宠主程序。Python 服务随桌宠发布和自动管理，不要求用户另外安装 Python。

1. 松手前停顿会将抛掷速度清零。

### 2.2 复用纪律

- Python 服务不得导入 PySide6、Qt 窗口或旧项目启动入口。
- 保留直接复制代码的来源、版权声明、版本指纹与修改说明。
- 旧项目的 WebM、FFmpeg、帧序列缓存和精灵绘制链不进入新产品。
- 不直接复制旧项目全部配置、插件系统、更新器或多宠生命周期。
- 源码许可证与角色素材声明分别登记；旧角色视频不作为新 3D 角色素材使用。
- 旧仓库的 `LICENSE` 为 MIT 文本；素材另见 `THIRD_PARTY_NOTICES.md`。不能把源码许可当成全部素材的统一许可。
- 研究中发现多屏文档与部分代码描述不一致。移植时复用规则、算法及回归用例，不直接照搬某一段架构说明。

### 2.3 两个 VRM 仓库：优先验证 AzPepoze，保留上游对照

主候选固定为 **AzPepoze `v2.6.1`**。该发布版本日期为 2026 年 9 月 22 日，包含 C++ 弹簧骨实现；其原生扩展声明最低 Godot 版本为 4.3，并提供 Windows x64 的调试和发布库。这是兼容性线索，仍需在本机 Godot 4.7.2 上实测。[S1][S2][S3]

对照候选固定为 **V-Sekai 提交 `e15199f980064028bfa4fbee5e70dddb82dd55c3`**。用于对比导入、材质、动画和弹簧骨行为，不同时装进同一工程。[S4]

| 项目 | AzPepoze | V-Sekai |
|---|---|---|
| 在本计划中的定位 | 首选生产候选 | 对照和回退候选 |
| 重点借用 | VRM 导入、MToon、C++ 弹簧骨、角色设置资源 | 导入与骨骼映射方法、表情动画轨道、样例及上游实现 |
| 需要重点验证 | 原生 DLL 导出、动作重定向、弹簧骨稳定性 | 相同模型下的运行开销和表现 |
| 安装目录 | `addons/vrm`、`addons/mtoon` | `addons/vrm`、`addons/Godot-MToon-Shader` |

两个 VRM 插件只服务于 VRM 资源及其专有能力。GLB / glTF 使用 Godot 的原生导入链，再接入同一个角色适配层和共享动作系统，不要求先转换成 VRM。[S7][S8]

两个版本的目录布局不同，不能混装。此前讨论中的独立 `addons/vrm1` 不适用于本次锁定的 V-Sekai 提交，应按实际仓库结构安装。

两者都存在需要应用侧完成的视线控制，以及与重定向相关的已知限制；AzPepoze 还明确记录了弹簧骨可能穿过碰撞体的问题。[S1][S4]

选型规则：

1. AzPepoze 通过导入、动画、表情、透明窗口、发布导出和性能门槛，采用该版本。
2. 若出现阻断问题，使用同一模型、相机和动作在 V-Sekai 对照工程重现。
3. 仅上游通过时，采用上游固定提交并重新导入角色包。
4. 两者均失败则停止进入后续阶段，记录最小复现；不通过改引擎版本或混合插件掩盖问题。
5. 不因“C++”就宣称性能更好，以本机同场景测量结果为准。

### 3.2 角色表现与桌面移动分离

角色内部使用真实 3D 骨骼、材质、转身和表情；桌面移动使用屏幕坐标计算。

- 相机采用固定正交视角，减少角色随位置变化产生的大小变化。
- 身体动作统一来自共享人形动作库；各模型通过适配配置对接，不按模型名称编写行为分支。
- 行走动画使用原地循环，由桌面移动模块推进窗口位置；角色包提供步幅与速度标定，避免不同腿长的模型滑步。
- 角色包定义脚底锚点、显示高度和动作最大包围范围。
- 首版默认角色显示高度约 300 个逻辑像素，允许用户缩放。
- 角色窗口大小覆盖全部首版动作，避免挥手或跌落时被裁切。
- 身体抛落与头发、衣物弹簧骨分别控制，不用弹簧骨替代角色整体物理。

行为采用本地状态机：

```text
idle → walk / react / dragged → falling → recover → idle
```

聊天、视线、表情和口型作为独立表现层。优先级固定为：

**隐藏或退出 > 用户拖拽 > 跌落恢复 > 用户指定动作 > 聊天回应 > 自主待机。**

首版不让模型逐帧控制骨骼，也不让模型生成执行代码。

### 3.3 Windows 窗口与鼠标输入

角色窗口保持透明、无边框、置顶且不夺取键盘焦点；只有用户主动打开聊天或设置时，相关窗口才获得焦点。

Godot 的穿透多边形在 Windows 上会影响绘制范围；整窗穿透标志的官方描述也不能直接当作跨应用穿透保证。因此，生产输入路径使用独立 Windows 适配层，并将“点击下面的其他程序”列为实机必测项。[S5]

采用以下实现：

- 角色包提供头部、躯干、四肢和大块衣物的交互形状。
- 根据当前骨骼姿态和相机投影更新屏幕交互区域。
- 光标落在交互区时接收输入，落在明显空白处时切换原生穿透状态。
- 首版不逐帧读取完整渲染图像，不实现发丝级 alpha 命中。
- 拖拽按下后保持捕获；正常松手、丢失捕获、隐藏、屏幕变化均调用同一收尾流程。
- 增加鼠标实际按键状态检查，防止丢失松手后永久挡住桌面。
- 所有原生窗口样式由一个模块管理，窗口重建后重新应用。

角色未占据屏幕的区域不创建大面积透明输入窗口。托盘始终提供“显示角色、恢复位置、关闭穿透、退出”入口。

### 3.4 屏幕坐标与持久化

应用内部使用显示器局部逻辑坐标；Windows 适配层统一处理物理像素换算。

持久化内容为：

- 显示器标识；
- 工作区内的相对位置；
- 角色逻辑高度；
- 角色包 ID；
- 面向方向。

首版支持通过设置选择显示器。拖拽活动限定在当前屏幕，不实现跨越屏幕接缝的连续拖动。

显示器断开时临时回到可用主屏；临时回退不覆盖原来的显示器偏好。增加“一键恢复到当前屏幕右下角”，避免虚拟显示器或分辨率变化导致角色丢失。

### 3.5 Godot 与 Python 服务通信

使用父子进程标准输入输出管道，不开放本地 HTTP 端口。

Godot 提供 `OS.execute_with_pipe()` 和非阻塞模式，但文档明确说明子进程不会自动随 Godot 退出。因此必须另做生命周期管理。[S6]

协议采用 UTF-8 单行 JSON，公共字段固定为：

| 字段 | 用途 |
|---|---|
| `version` | 协议版本，首版为 1 |
| `id` | 请求 ID |
| `type` | 请求或事件类型 |
| `session_id` | 会话归属，无会话操作可省略 |
| `payload` | 对应类型的数据 |

首版命令：

- `hello`、`settings.get`、`settings.update`
- `chat.send`、`chat.cancel`
- `memory.list`、`memory.upsert`、`memory.delete`
- `tts.synthesize`、`tts.cancel`
- `shutdown`

首版事件：

- `ready`、`chat.delta`、`chat.done`
- `audio.ready`、`cancelled`、`error`

固定约束：

- stdout 只写协议，日志进入 stderr。
- 双方处理拆包、半行、连续多行和中文分片。
- 单行消息上限 1 MiB；音频通过受控缓存文件传递。
- 每次聊天、角色切换和音频播放都携带请求归属；过期结果不再更新界面。
- 同时只执行一个主聊天请求；新请求先取消旧请求。
- 服务故障时角色仍可待机和拖拽，聊天显示可恢复错误。
- 服务异常退出允许一次自动重启，不自动重复发送用户消息。
- 正常退出先停止接单并排空存储；强制结束主程序时，通过 Windows Job Object 回收自有服务进程。

### 3.6 数据与角色接口

数据默认保存在 `%LOCALAPPDATA%\Pet3D\`，与程序目录分离：

- 设置使用版本化 JSON，原子替换。
- 会话和记忆使用 SQLite，由 Python 服务单独写入。
- API Key 使用 Windows 凭据存储；存储不可用时仅保留本次会话，并明确显示未持久保存。
- 音频缓存按文本、音色、速度、后端和版本组成缓存键，设置容量上限。
- 首版不自动迁移旧桌宠存档。

角色清单至少包含：

`schema_version、id、version、scene、display_name、source_format、skeleton_profile、skeleton_path、bone_map、rest_adjustment、motion_library、action_map、foot_anchor、default_height、locomotion、expressions、hit_shapes、capabilities、license`

其中 `scene` 指向打包后的 Godot 场景；`motion_library` 引用统一动作库 ID 与版本，`action_map` 将统一动作名绑定到动画资源；`bone_map` 和 `rest_adjustment` 保存模型首次适配结果；`locomotion` 保存步幅及速度标定。`capabilities` 明确表情、口型和次级运动是否可用，不能把缺失能力伪装成已支持。

统一角色适配接口：

- `load_character(id)`
- `play_action(name)`
- `set_expression(name, weight)`
- `set_look_target(position)`
- `set_mouth_open(weight)`
- `set_secondary_motion_enabled(enabled)`

插件内部节点名和目录结构只在角色适配模块中使用，聊天和行为模块不直接访问。

首版角色包随应用发布，只加载预先验证的包，不接受任意第三方 PCK 或脚本。新增角色在开发制作流程中导入、适配和验证后随应用发布；首版不包含用户在运行中直接导入任意 VRM / GLB / glTF 的功能。

### 3.7 多模型兼容与共享动作工作流

**目标：动作制作只维护一套来源；每个新角色做一次适配，以后切换角色沿用同一套动作、聊天和行为逻辑。**

#### 3.7.1 模型支持边界

| 模型情况 | 首版处理 |
|---|---|
| 带骨骼、正确蒙皮的人形 VRM | 通过锁定的 VRM 插件导入，再接入统一角色适配层 |
| 带骨骼、正确蒙皮的人形 GLB / glTF | 通过 Godot 原生 glTF 导入；完成骨骼映射和姿势校正后使用共享动作 |
| 无骨骼或无蒙皮的静态 GLB / glTF | 标记为尚未达到角色包条件；需先在制作工具中绑定骨骼和权重，不承诺自动获得人物动作 |
| FBX 等其他创作格式 | 作为制作素材，先转换为并验证 GLB，再进入相同流程；首版不承诺直接兼容所有原始格式 |
| 猫、狗、机械体等非人形骨架 | 不使用本版人形动作库；后续独立建立骨架规范、适配器和动作库 |

`.gltf` 的外部纹理和二进制依赖必须一并收集；格式、资源路径和依赖完整性作为导入校验的一部分。[S8]

#### 3.7.2 统一骨骼与一次性适配

- 将 Godot `SkeletonProfileHumanoid` 作为人形映射基础，为每个角色建立 `BoneMap`；骨骼同名不等于已经兼容。[S7]
- 验证骨骼父子关系、蒙皮、朝向、单位、根变换及左右手脚对应关系；缺少公共动作所需的骨骼时拒绝将该角色标为可发布。
- 将 T-Pose / A-Pose 和骨骼静止姿势的差异记录为模型适配配置，按 Godot 重定向流程校正，禁止通过修改所有公共动作来迁就一个角色。
- 保留每个角色的身体比例；分别标定脚底锚点、显示尺寸、步幅、运动速度和交互形状。
- 导入及构建过程中允许生成每模型的轨道绑定或重定向缓存，但动作的创作源与版本只有一份；不人工复制整套动作后分别维护。
- 所有骨骼节点路径、插件差异及姿势校正仅由角色适配层管理，聊天与行为模块不直接引用模型内部节点。

#### 3.7.3 共享动作库

公共库 ID 固定为 `humanoid_core`，初始接口版本为 `1`；标准动作名为：

`idle、walk、turn、wave、pickup、fall、recover`

- 动作独立导入为 Godot `AnimationLibrary` 资源，由统一角色适配器加载和绑定。[S9]
- 身体动作轨道只控制统一人形骨架，不写入角色特定的网格名、材质名或面部 Blend Shape 名。
- 行走不携带桌面平移；位移由桌面行为模块控制，播放速度与角色步幅配置联动。
- 姿势差异通过重定向适配解决；严重超出人形动作适用范围的模型不通过角色包验收。
- 更新公共动作时，所有已适配角色自动纳入回归矩阵，不能只在制作动作时使用的角色上验证。

#### 3.7.4 表情、口型、材质与次级运动

- 身体骨骼动作与表情轨道分开。每个角色把眨眼、情绪、张嘴映射到自身的 Blend Shape 或受支持的面部骨骼。[S10]
- 缺少可选情绪表情时保持中性；口型无可用驱动时明确标记为不支持，可正常朗读但不宣称口型已通过。首版正式主角色必须有可用的口型驱动。
- 表情、视线和口型有独立权重与复位规则，防止身体动作覆盖嘴部、表情覆盖眨眼或停止语音后嘴部残留。
- VRM 使用其 MToon、元数据及次级运动配置；普通 GLB / glTF 保留已验证的材质，不强行转换成 MToon。
- 普通 GLB / glTF 不默认具有 VRM 弹簧骨、表情命名或授权元数据；缺少次级运动时保持关闭，其他角色能力仍可运行。

#### 3.7.5 新角色加入与切换流程

1. 放入源模型及授权说明，检查依赖、骨骼和蒙皮。
2. 生成或配置骨骼映射、静止姿势修正和统一动作绑定。
3. 标定尺寸、脚底、步幅、视线范围和身体交互区。
4. 配置表情、口型和次级运动能力，并生成角色清单。
5. 在共享动作测试场景中逐一播放全部标准动作，检查扭曲、滑步、裁切和资源缺失。
6. 导出经验证的预制角色包，加入角色列表；不修改聊天、行为状态机或公共动作源文件。
7. 运行时先在未显示状态加载新包并检查必需资源；检查通过后停止旧音频与动作，再切换角色并释放旧资源。加载失败时保留原角色，给出可读原因。

已经完成这些步骤的角色包可以直接切换；新找到的原始模型首次仍需经过适配，不能以文件后缀相同作为兼容保证。

### 5.2 必须实机验证的项目

以下项目不能用单元测试通过替代：

- 在桌面、资源管理器、浏览器和记事本上方穿透。
- 点击角色后原应用继续接受键盘输入。
- 拖拽中 Alt+Tab、弹窗、隐藏、锁屏和恢复。
- 全屏应用出现时执行已配置的隐藏策略。
- 100%、125%、150% 缩放下的可见位置与点击范围。
- 有实际设备时测试多屏负坐标、拔插和恢复；没有设备则标注未验证。
- 一个 VRM 和两个不同体型 GLB 在导出包中播放同一套动作，检查滑步、脚底、骨骼扭曲、窗口裁切和点击区域。
- 导出包中的材质、可用表情、口型、弹簧骨和语音；切换角色后旧模型和旧声音不残留。
- 强制结束主程序后的后台进程清理。

### 5.3 首版性能预算

以下数字是开发验收目标，不是当前实测结果。基准场景为：单角色、默认尺寸、预热 5 分钟；统计包含 Godot 和 Python 服务，排除用户另外运行的模型服务。

| 场景 | 目标 |
|---|---|
| 普通待机 | 30 FPS，整机口径平均 CPU ≤ 2% |
| 隐藏且无聊天、合成任务 | 平均 CPU ≤ 0.5%，角色停止重绘 |
| 拖拽及基础抛落 | 目标 60 FPS，P95 帧耗时 ≤ 20 ms |
| 默认角色稳定运行 | 总工作集目标 ≤ 500 MiB，独立显存目标 ≤ 350 MiB |
| 2 小时运行 | 无持续线性内存增长；重复操作结束后回到稳定区间 |
| 用户停止语音 | 本地停止播放及嘴部复位目标 ≤ 150 ms |

同时记录 GPU 引擎、平均功耗或可取得的电源指标、接电与电池状态。不能只因显卡性能充足而忽略常驻耗电。

如未达到预算，按“帧率 → 弹簧骨数量 → 材质与贴图 → 轮询与绘制策略”顺序定位；发布前必须记录超标原因和实际结果，不能静默放宽指标。

### 5.4 每阶段交付

每个阶段的可运行产物保存在工作根目录的 `dist\stage-0\` 至 `dist\stage-6\` 对应目录；报告、测试记录、性能读数、日志、截图及录像保存在 `docs\reports\` 下同名阶段目录。最终完成文件按 §3.1 汇总到 `dist\Pet3D\`，并打包为首版压缩包。

每个阶段都交付：

1. 可运行的阶段产物。
2. 改动及代码复用来源清单。
3. 自动测试结果与必要的实机截图或短录像；角色阶段同时交付三模型共享动作兼容矩阵和逐模型适配记录。
4. 性能测量的环境、采样时长和读数。
5. 尚未通过的项目及下一步定位依据。

首版完成标准：用户能独立启动桌宠，看到真实 3D 角色沿底边活动，正常拖拽和点击，不妨碍桌面操作；能完成聊天、保存并查看记忆、朗读与口型同步；断网和服务故障时基础互动继续工作；最终目录包可运行、可恢复位置、可完整退出；一个 VRM 和两个不同体型 GLB 经一次性适配后复用同一套动作，切换时无需修改业务代码。

后续版本再分别增加音乐反应与指定应用联动、按键语音输入、运行时用户 VRM / GLB / glTF 导入、多宠及沿软件窗口活动。每项单独验证，不并入首版验收。
